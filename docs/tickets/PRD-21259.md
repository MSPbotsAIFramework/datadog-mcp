## Requirement understanding

One line: Connect Datadog as an MCP integration so Claude, ChatGPT, Cursor, or any MCP-compatible AI client gets live access to Datadog, with credentials encrypted and every action logged.

The ticket is a one-line connector request from the `[Network]` intake bucket: give Agent-platform AI clients live, MSPbots-gateway-mediated access to a customer's Datadog account (monitors, logs, metrics) so they can answer questions and take limited actions against Datadog without a human opening the Datadog console. Credential encryption and action logging are platform-gateway responsibilities (per-record credential encryption, audit log of every tool call — see Current state), not something this repository implements itself; this repository's job is to expose Datadog as a well-behaved MCP service that the gateway can front.

## Product design

### Goals / Non-goals

Goals (first version):
- Build `MSPbotsAIFramework/datadog-mcp` as a contract-compliant MCP service (Streamable HTTP, stateless, per-request credentials) per `vendor-mcp-development-sop.md`.
- Cover the three capabilities the ticket and the repo's own placeholder description point at: **monitors**, **logs**, **metrics** — plus **events**, which sits naturally alongside monitors/logs for the "what happened and why" investigative flows an AI assistant is used for.
- Support all Datadog sites/regions (US1/US3/US5, EU, AP1, GovCloud) via one optional header, so the connector works for any tenant's Datadog account regardless of which site it lives on.

Non-goals (explicitly out of scope for v1 — see Decisions made by DEV01 for why):
- Creating, editing, or deleting monitors; submitting metrics or logs; posting events. All v1 tools are read-only except mute/unmute (see AC3), which are reversible and scoped to a single named monitor.
- Dashboards, SLOs, Synthetics, APM traces/spans, Incidents, RUM, Security Monitoring signals, Cloud Cost — all separate Datadog product surfaces with their own API families; adding them is a straightforward follow-up (new `tools/<resource>.py` files) once there is a concrete need, not a v1 blocker.
- Building or changing the tenant-facing "Connect Datadog" UI/connector form — that is a platform/gateway concern (`ProductDocs/18-Dev.md § Published Connectors`), unaffected by this repo.
- Credential encryption at rest and tool-call audit logging — both are properties of the MSPbots gateway that fronts every vendor MCP, not of this service (SOP §0.2 "Operating model"); this service's only credential obligation is to read them from per-request headers and never persist or log them (see Non-functional).

### Acceptance criteria

- **AC1** — Given a valid `X-Datadog-Api-Key` and `X-Datadog-Application-Key`, When the client calls `datadog_search_monitors` with no filter, Then it receives a bounded list of monitor summaries (id, name, type, overall state, tags, query) with pagination info (`page`, `per_page`, `has_more`), not an unbounded dump of every monitor.
- **AC2** — Given the same credentials and a known `monitor_id`, When the client calls `datadog_get_monitor`, Then it receives the full monitor detail (definition, state, tags, options); When the `monitor_id` does not exist, Then it receives a structured `not_found` error, not a 500 or a stack trace.
- **AC3** — Given a known `monitor_id`, When the client calls `datadog_mute_monitor` with an optional scope and end time, Then the monitor is muted and the response confirms the new muted state; When the client later calls `datadog_unmute_monitor` for the same monitor, Then the mute is cleared and the response confirms the monitor is active again.
- **AC4** — Given valid credentials and a time range, When the client calls `datadog_search_logs` with a query string, Then it receives matching log events (bounded page size, cursor for the next page) and an empty result set when nothing matches — never a `not_found` error for "no logs matched".
- **AC5** — Given valid credentials, a metric query string (e.g. `avg:system.cpu.user{*}`), and a time range, When the client calls `datadog_query_metrics`, Then it receives the timeseries points for that query over that range, with a clear, structured error (not a silent empty series) when the query string itself is invalid.
- **AC6** — Given valid credentials and a "since" timestamp, When the client calls `datadog_list_active_metrics`, Then it receives the set of metric names reported active since that time, truncated with `has_more` when the account has more active metric names than the response cap — never an unbounded multi-thousand-name dump.
- **AC7** — Given valid credentials and a time range, When the client calls `datadog_search_events` with a query string, Then it receives matching events (bounded page size, cursor for more) and an empty result set (not `not_found`) when nothing matches.
- **AC8** — Given a request to any tool that is missing a required credential header, When the tool is called, Then the service returns HTTP 401 listing the missing header name(s) — never a 500, and never a call that reaches the Datadog API with an empty/placeholder credential.
- **AC9** (multi-tenant isolation) — Given two concurrent requests that carry two different tenants' Datadog credentials, When both are in flight against this service at the same time, Then each response reflects only its own request's credentials and data — never the other tenant's, and never a leftover credential from a prior request on the same instance.
- **AC10** (region/site support) — Given a request that sets `X-Datadog-Site` to a non-default site (e.g. `datadoghq.eu`, `us3.datadoghq.com`), When any tool is called, Then the service calls that site's API base URL, not the US1 default; Given the header is omitted, Then the service defaults to `datadoghq.com` (US1).
- **AC11** (upstream failure handling) — Given Datadog's API returns a rate-limit response (429) or a 5xx, When a tool call hits that response, Then the service retries a bounded number of times with backoff and, if still failing, returns a structured `rate_limited` or `upstream_error` (respectively) with `retryable: true` — never an unhandled exception.

### Open questions

- [not blocking] The ticket does not say whether write access (mute/unmute) is wanted at all, versus a purely read-only connector. Assumption: include mute/unmute because they are reversible, low-risk, and are the one Datadog write operation an AI ops assistant plausibly needs ("silence this noisy monitor for an hour") without touching monitor *definitions*. If this assumption is wrong, dropping these two tools is a small, isolated change (remove `tools/monitors.py`'s two write functions; no contract impact on the other six tools).
- [not blocking] Dashboards/Incidents/APM are not in v1 (see Non-goals). If a specific one of these turns out to be the actual need, that is a scoped follow-up ticket, not a reason to block this one — the ticket text only names "monitors, logs, metrics" (plus, generically, "live access").

## Tech design

### Conclusion

Build `MSPbotsAIFramework/datadog-mcp` from scratch (Main line A, clean-room against Datadog's public API docs) as a Python 3.12 + uv + FastMCP service with 8 tools across 4 resource domains (monitors, logs, metrics, events); credentials read per-request from two required headers plus one optional site header that selects the regional base URL. No alternative implementation approach applies — this is a new, single-purpose connector with one natural shape dictated by the SOP.

### Where the current implementation lives

Nothing to build on: `README.md:1-2` is the entire repo content at `0ab3ff3`. No prior Datadog code exists anywhere in `MSPbotsAIFramework` (Current state). The nearest same-shape references are other already-built MSPbotsAIFramework `<vendor>-mcp` services following the same SOP structure (`src/<vendor>_mcp/{config,api_client,server}.py` + `tools/<resource>.py`, per `vendor-mcp-development-sop.md` §9) — this design follows that structure exactly rather than inventing a new one.

### Option analysis

No alternative: the SOP mandates a clean-room, self-built MCP service per vendor (no forking/mirroring open-source Datadog MCP servers — SOP rule 3), a fixed transport contract (Streamable HTTP, stateless), and a fixed credential model (per-request headers). The only real decision points are *which* Datadog capabilities to expose and how to shape the tools — covered in "Decisions made by DEV01" below, not as competing architectures.

### 4a. Reuse & cleanup

- **Reuse**: FastMCP (`mcp[cli]`) for the protocol layer, `httpx` for the outbound client, `pydantic-settings` for config — all per SOP §9, no custom HTTP/protocol code. The repo structure, tool-registration pattern (`register(mcp, client_factory)` per resource file), and error envelope are copied from the SOP's recommended shape rather than invented.
- **New dependencies**: `mcp[cli]>=1.9.0,<2.0.0` (MCP protocol + FastMCP, SOP-recommended, version-pinned per SOP §9); `httpx` (async HTTP client, replaces hand-rolled `requests`/sockets); `pydantic-settings` (env parsing with `extra="ignore"`). No other third-party deps planned; Datadog has official client SDKs (`datadog-api-client` Python package) but it is not used here — it targets direct end-user scripting (sync, OpenAPI-generated, heavier dependency surface) rather than the per-request-header / async / request-scoped-credential model this service requires, and the API surface needed (8 read-mostly operations) is small enough that a direct `httpx` client is simpler to keep contract-correct (error mapping, timeouts, retries) than adapting a generated SDK built around a single configured client instance.
- **API/tool signatures**: see Data & API contract below; every `list`/`search` tool takes the same two-parameter shape (`limit` default ≤ 50 / hard cap ≤ 200, plus a cursor or `page`) so the pattern is consistent across resource domains rather than bespoke per tool.
- **In-scope cleanup**: none — there is no existing code in this repo to clean up (scaffold only).
- **Suggested follow-ups** (out of this ticket's scope): once a concrete need appears, Dashboards/Incidents/APM/Synthetics would each be a new `tools/<resource>.py` file added to this same repo, not a new repo — flagged here so a future ticket does not duplicate the scaffold work.

### Data & API contract

**Credential headers** (declared in README per SOP §3.1):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Datadog-Api-Key` | Yes | Datadog API key | Datadog → Organization Settings → API Keys |
| `X-Datadog-Application-Key` | Yes | Datadog Application key | Datadog → Organization Settings → Application Keys |
| `X-Datadog-Site` | No (default `datadoghq.com`) | Which Datadog site/region the account lives on | Datadog → user menu → My Preferences (shows the account's site) |

Both `DD-API-KEY` and `DD-APPLICATION-KEY` are required on every tool, not just the subset Datadog's own docs mark as application-key-required — see Decisions made by DEV01 for why.

**Site → base URL** (`api_client.py` lookup table, from https://docs.datadoghq.com/getting_started/site/):

| `X-Datadog-Site` value | Base URL |
|---|---|
| `datadoghq.com` (default) | `https://api.datadoghq.com` |
| `datadoghq.eu` | `https://api.datadoghq.eu` |
| `us3.datadoghq.com` | `https://api.us3.datadoghq.com` |
| `us5.datadoghq.com` | `https://api.us5.datadoghq.com` |
| `ap1.datadoghq.com` | `https://api.ap1.datadoghq.com` |
| `ddog-gov.com` | `https://api.ddog-gov.com` |

Unrecognized value → `invalid_argument` error naming the accepted values, not a silent fallback to US1.

**Tools** (all return a JSON string per SOP §4.1; errors use the SOP §4.2 envelope `{"error":{"code","message","retryable"}}`):

| Tool | Upstream | Method/Path | Key params | Hints |
|---|---|---|---|---|
| `datadog_search_monitors` | Monitors | `GET /api/v1/monitor/search` | `query` (optional), `page`, `per_page` (default 30, cap 100) | `readOnlyHint` |
| `datadog_get_monitor` | Monitors | `GET /api/v1/monitor/{monitor_id}` | `monitor_id` | `readOnlyHint` |
| `datadog_mute_monitor` | Monitors | `POST /api/v1/monitor/{monitor_id}/mute` | `monitor_id`, `scope` (optional), `end` (optional epoch seconds) | `destructiveHint=false` (reversible), not idempotent (repeated calls extend/replace the mute window) |
| `datadog_unmute_monitor` | Monitors | `POST /api/v1/monitor/{monitor_id}/unmute` | `monitor_id`, `scope` (optional) | `idempotentHint` (unmuting an already-active monitor is a no-op) |
| `datadog_search_logs` | Logs | `POST /api/v2/logs/events/search` | `query`, `from`, `to` (RFC3339 or relative, e.g. `now-15m`), `limit` (default 50, cap 200), `cursor` (optional) | `readOnlyHint` |
| `datadog_query_metrics` | Metrics | `GET /api/v1/query` | `query` (Datadog metric query string), `from`, `to` (epoch seconds) | `readOnlyHint` |
| `datadog_list_active_metrics` | Metrics | `GET /api/v1/metrics` | `from` (epoch seconds), `prefix` (optional, client-side filter on the returned names), `limit` (default 50, cap 200) | `readOnlyHint` |
| `datadog_search_events` | Events | `POST /api/v2/events/search` | `query`, `from`, `to`, `limit` (default 50, cap 200), `cursor` (optional) | `readOnlyHint` |

Example — `datadog_search_monitors` response (truncated, compact JSON, no `indent`):

```json
{"monitors":[{"id":12345,"name":"High CPU - web-01","type":"metric alert","overall_state":"Alert","tags":["env:prod","team:platform"],"query":"avg(last_5m):avg:system.cpu.user{host:web-01} > 90"}],"page":0,"per_page":30,"has_more":true}
```

Example — error envelope (missing monitor):

```json
{"error":{"code":"not_found","message":"Monitor 999999999 does not exist.","retryable":false}}
```

**No DB, no persistence, no migration** — this service is stateless by contract (SOP §1.3); nothing to add to this section beyond "there is none."

**Backward compatibility**: not applicable — first version of a new service, no prior consumers.

### Key flow / sequence

```
Agent (via MSPbots Gateway)
  -> POST /mcp  {tools/call: datadog_search_monitors, query: "status:alert"}
     Header: X-Datadog-Api-Key, X-Datadog-Application-Key[, X-Datadog-Site]
  -> server.py middleware: reads headers, sets ContextVar, calls tool, `finally: reset`
  -> tools/monitors.py: client_factory() builds api_client.Client from ContextVar
  -> api_client.py: GET {site_base_url}/api/v1/monitor/search?query=status:alert&per_page=30
     (connect 5s / read 30s timeout; retry 429/5xx with backoff, respecting Retry-After)
  <- Datadog API: 200 + monitor list, or 4xx/5xx
  -> tools/monitors.py: maps success -> trimmed JSON (id/name/type/overall_state/tags/query, paged);
                         maps failure -> error envelope via errors.py status_code map
  <- MCP response (JSON string) -> Gateway -> Agent
```

### Non-functional

- **Idempotency & concurrency**: all tools except `datadog_mute_monitor` are naturally idempotent (reads, or an unmute that is a no-op when already unmuted). `datadog_mute_monitor` is not idempotent by design (Datadog itself treats repeated mute calls as updating the mute window) — documented in the tool description so the Agent does not assume safe blind retries change nothing.
- **Performance**: all `list`/`search` tools cap `limit` at ≤ 200 and default to ≤ 50 (SOP §2.5); `datadog_list_active_metrics` additionally truncates and sets `has_more` rather than returning Datadog's full (potentially thousands-of-names) response, since that endpoint has no native page size (see Decisions made by DEV01). Outbound calls: 5s connect / 30s read timeout, bounded retries on 429/5xx, single HTTP client reused per request (SOP §5).
- **Security**: credentials read only from the three headers above, never from env/config (SOP §3.1); request-scoped via `ContextVar`, reset in `finally` (SOP §3.3); no cross-request caching of credentials, tokens, or fetched data (SOP §3.4); error messages never include the raw Datadog response body or the credential headers (SOP §4.2 note, §6).
- **Multi-tenant isolation**: covered by the same request-scoped-credential mechanism — there is no shared state between requests to leak across tenants (AC9); verified by a concurrency test in `test_middleware.py`.
- **Observability**: structured logs (tool name, request id, upstream path + status code, latency, error `code`) per SOP §6; never log header values or response bodies verbatim.

### Risks & dependencies

- **Risk**: `datadog_list_active_metrics` has no native upstream page size; a very active account could have tens of thousands of metric names. Mitigated by the client-side cap + `has_more` + optional `prefix` filter (Decisions made by DEV01); residual risk is a single oversized upstream response before truncation — acceptable since it is a GET with a bounded timeout, not unbounded memory growth across requests.
- **Risk**: requiring both `DD-API-KEY` and `DD-APPLICATION-KEY` on every tool is slightly stricter than Datadog's own per-endpoint rules; a tenant that only generated an API key (no Application key) gets a 401 on tools that technically wouldn't need one. Accepted trade-off, see Decisions made by DEV01.
- **Dependency**: INT registration (`/api/vendor-register`) is owned by the review leg, not this ticket — flagged so the review leg knows this is a first-time registration, not an update.
- **Dependency**: no real Datadog account for end-to-end verification before INT (not a blocker per SOP; flagged as "needs a real vendor account" in the ledger).
- **Not a risk**: the ticket's Conduit link (`conduit.wyre.ai/plugins/datadog`) is marketing material for a different product (Conduit/WYRE AI's own plugin marketplace), not a dependency of this MCP service; it is not referenced anywhere in the implementation.

### Decisions made by DEV01

No one was available to ask for a first version with these choices (`mcp-track.md` 2.4). Each is small and reversible:

- **Tool scope: monitors + logs + metrics + events, 8 tools total, read-first.** Monitors/logs/metrics are explicitly named by the ticket and the repo's own placeholder description; events is added because it is the natural fourth leg of "what's wrong and why" investigative workflows (an Agent debugging an alert will often want the events timeline alongside the monitor and the metric). Dashboards/Incidents/APM/Synthetics/SLOs are left out of v1 — none are named in the ticket, and each is its own API family better added as a follow-up `tools/<resource>.py` once there is a concrete need. Alternative considered: mirror every Datadog API endpoint 1:1 — rejected per SOP §2.1 ("capabilities, not endpoint mirrors") and the ≤20-tool guidance.
- **Write tools limited to mute/unmute.** These are reversible, scoped to one named monitor, and match a real "AI ops assistant" use case (silence a noisy alert). Creating/editing/deleting monitors, or any log/metric/event ingestion, is excluded — those are higher-blast-radius writes with no stated need in the ticket (SOP §2.7 "default to read-only"). Alternative: fully read-only v1 — rejected because mute/unmute is low-risk and high-value enough to include now rather than as a second round.
- **Both credential headers required on every tool, not per-endpoint as Datadog's docs allow.** Datadog's own API technically lets some read endpoints work with only `DD-API-KEY`. Requiring both uniformly means a single 401 behavior and a single README row set the Agent (and whoever wires up the tenant's credentials) has to understand, instead of a per-tool matrix that is easy to get wrong on either side. Alternative: per-tool minimal requirement — rejected for the uniformity reason above; revisit if a tenant without an Application key becomes a real case.
- **`datadog_list_active_metrics` truncates client-side with an optional `prefix` filter**, since the upstream endpoint (`GET /api/v1/metrics`) has no page-size parameter and can return very large result sets on active accounts. Alternative: drop the tool entirely — rejected because metric-name discovery is the natural precursor to `datadog_query_metrics` (an Agent needs to know what metric names exist before it can query one); alternative: return everything uncapped — rejected per SOP §2.5 token-economy rules.
- **Site/region as one optional header with a lookup table, defaulting to `datadoghq.com`.** Keeps multi-region support to a single extra header rather than requiring a full base-URL string from the caller (which would let a misconfigured caller point at an arbitrary host). Alternative: accept a raw `X-Datadog-Base-Url` override — rejected as an unnecessary larger attack surface for a need (6 known Datadog sites) a fixed lookup table already covers; can be added later if a 7th site appears before this table is updated.
